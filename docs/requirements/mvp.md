# Whippet MVP 規格

狀態：需求基線已確認；本文件細節為可直接實作的預設。各階段實作與驗收以 docs/tracking/implementation.md 為準。

## 目標

讓不懂 Playwright 的 QA 在 self-hosted 網頁平台透過對話建立 Playwright 測試，實際驗證、確認發佈後，由遠端執行節點執行並查看報告與即時畫面。

## MVP 範圍

| 功能 | 行為 |
| --- | --- |
| 登入 | 點擊登入取得後端固定開發用 Superadmin 身分；不收帳密 |
| Workspace | 支援建立、切換及修改多個 Workspace；目前全為 Superadmin，資源存取保留共同授權入口 |
| Workspace 設定 | 透過 AI 對話建立驗測目的、網站範圍、登入角色與背景；機密獨立輸入與保存，模型金鑰仍以部署 secret 注入 |
| 測試列表 | 顯示名稱、描述、發佈版本及最近執行結果；可建立、編輯與執行 |
| 測試詳情 | 一般模式依序為標題、說明、最近一次執行、歷史紀錄、歷史版本、唯讀腳本 |
| 編輯 | 新建／修改時右側為完整對話工作區；AI 修改腳本，驗證、監看、結果與確認操作嵌入對話 |
| 草稿 | 每個 Test 最多一個活躍編輯週期，保留 revision 與專屬對話；可續編或確認放棄 |
| 發佈 | 同一 revision 成功驗證、報告保存、AI 完成版本說明與背景摘要，再由 QA 明確確認發佈 |
| 執行 | 固定已發佈版本；支援排隊、執行、取消、逾時及失敗 |
| 報告 | 結果摘要、時間、錯誤與日誌；正常完成提供 Playwright HTML report；失敗保留可取得的 trace／截圖 |
| 監看 | 執行期間唯讀畫面；WebRTC 主路徑、可替換備援；監看中斷不停止測試 |
| Agent | OpenAI-compatible 模型服務；工具可探索網站、讀寫草稿、執行驗證 |
| Manager | 單一啟用 Manager、多個一次性 Worker；共用最大併發設定 |
| 通訊 | Manager 主動連 Server WebSocket；支援重連與任務狀態對帳 |
| 部署 | Linux Docker Server；Linux／Mac Docker 執行節點；MVP Chromium |

## 主要流程

1. 點擊登入 → 選擇或建立 Workspace → 對話確認驗測目的與網站範圍 → 受限探索與登入資訊收集 → 確認保存設定。
2. 新建 Test → 說明步驟與預期結果 → Agent 產生草稿 → 儲存。
3. 執行草稿驗證 → 查看結果與畫面 → 在同一對話繼續修改。
4. 最新 revision 驗證通過且報告保存 → QA 確認 → 發佈不可變版本。
5. 從 Test 詳情執行已發佈版本 → 排隊／監看 → 查看歷史與報告。
6. 離開再返回可恢復已保存的對話與草稿；不承諾保留原本瀏覽器記憶體狀態。

## 業務規則

- Test 是可執行的測試資產，與 Playwright 的 project 設定不同；MVP 可先是一份 spec 加必要支援檔。
- 草稿修改產生新 revision；樂觀鎖避免多人編輯時靜默覆寫。衝突提示重新載入即可，不做協作編輯。
- 驗證綁定 revision、程式內容雜湊、執行設定快照與 Worker 映像版本。相關內容變動後重新驗證。
- 未發佈 Test 可驗證草稿；一般執行按鈕只執行已發佈版本。
- 正式失敗保留原版本；Agent 修復進入草稿，再走驗證與確認。
- 對話等待使用者期間釋放 Worker。工具執行／驗證與正式測試共用 FIFO 佇列與併發上限。
- 模型服務失敗時回報可重試錯誤並保留草稿；已發佈的純腳本執行不依賴模型可用性。
- Worker 異常：保存可取得證據、回收程序與容器、確認回收才放行下一個任務。
- 連線中斷不自動重新執行任務；執行結果未知時呈現中斷／待對帳，避免重複操作被測網站。

## MVP 不實作

真實登入／RBAC、多 Manager 排程、Polling／HTTP Push adapter、SSO／MFA、人工遠端操控、多人即時協作、排程／CI 觸發、跨瀏覽器矩陣、自動修復後發佈、完整配額與稽核系統。

保留資料欄位或介面即可，不建立完整外掛框架。被測網站的 SSO 與平台登入是不同功能。

## 2026-11-12 已確認擴充

詳細互動與業務規則見 [AI 對話工作區規格](ai-workspace.md)，覆蓋歷史單 Workspace／直接編輯腳本的 UI 範圍。本輪包含多 Workspace，仍不包含平台真實登入／RBAC、被測網站 SSO／MFA／驗證碼自動化或本機瀏覽器執行。

## 最小交付條件

- QA 能完成建立、對話修改、儲存草稿、驗證、確認發佈與正式執行，並看到同版本報告。
- 舊 revision 的成功不能放行新 revision；失敗或缺少報告也不能發佈。
- 併發上限設為 1，第二個任務等待；第一個停止且資源回收後第二個才開始。
- Manager 重連不產生重複執行；可在代表性的 Mac Docker 節點完成一個任務。
- 有可觀看的執行畫面；WebRTC 與備援各自的實際驗證狀態如實記錄。

MVP 驗證方式與開發順序見 [實作計畫](../tracking/implementation.md)。
